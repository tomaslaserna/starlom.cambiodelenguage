# Supplier 360 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convertir el directorio de proveedores en una ficha 360 interna, editable y auditada, con datos maestros, productos asociados, compras y saldo pendiente calculados desde la operatoria real.

**Architecture:** Mantener `suppliers` como registro maestro de un único contacto y una única cuenta bancaria, ampliar su esquema mediante una migración aditiva y centralizar validación/mapeo en `catalog-management.ts`. Separar la lectura agregada en `supplier-detail.ts`, renderizarla desde una ruta dinámica Server Component y usar una Server Action con `useActionState` para edición con errores recuperables; la API privada reutiliza el mismo dominio. Los indicadores nunca se persisten: se calculan desde `purchases` y `products`, siempre filtrados por `empresa_id`.

**Tech Stack:** Next.js 16.3.3 App Router, React 19.2.4, TypeScript, PostgreSQL/Supabase, Server Components, Server Actions, Node.js test runner.

**Spec:** `docs/superpowers/specs/2026-11-20-supplier-360-design.md`

## Global Constraints

- Trabajar únicamente con proveedores activos; no agregar estado, filtro de inactivos ni reactivación.
- Mantener un solo contacto principal y una sola cuenta bancaria por proveedor.
- Lectura requiere `proveedores.ver`; edición requiere `proveedores.editar`.
- Toda lectura y escritura debe incluir `empresa_id`; un UUID de otra empresa se trata como inexistente.
- No exponer datos bancarios en `/suppliers`, búsquedas globales ni endpoints públicos.
- No registrar pagos, compras ni movimientos de stock desde la ficha; sólo enlazar a circuitos existentes.
- `legal_name` es razón social y no se reinterpretará; `contact_name` es el contacto principal nuevo.
- Total comprado y cantidad de compras sólo cuentan `purchases.status = 'recibida'`; saldo pendiente es `GREATEST(total_amount - paid_amount, 0)` sobre compras recibidas.
- La edición debe ser atómica y registrar `supplier.updated` en `audit_log` con valores anteriores y nuevos.
- Crear la migración con `supabase migration new supplier_360_fields`; no inventar el timestamp del archivo.
- Por el cambio de Supabase CLI v3, descubrir y confirmar los comandos con `npx supabase --help` y usar opciones explícitas de destino; no aplicar cambios remotos durante las tareas de implementación.

## Review Focus

- CUIT y CBU/CVU con espacios, guiones o letras: normalizar a dígitos y rechazar longitudes distintas de 11 y 22 respectivamente; Task 2 lo fija con pruebas de validación.
- UUID de proveedor válido pero perteneciente a otra empresa o inactivo: devolver 404 sin filtrar datos maestros, bancarios ni actividad; Tasks 2 y 3 lo fijan mediante SQL y mocks con `empresa_id`/`active`.
- Compras canceladas, pendientes, parcialmente pagadas o sin fecha: sólo las recibidas alimentan métricas, el saldo nunca es negativo y el historial sigue siendo trazable; Task 3 lo fija con filas mixtas.
- Error de validación o base durante la edición: mantener el modal y los valores ingresados, mostrar un mensaje concreto y no escribir auditoría parcial; Tasks 2 y 5 cubren atomicidad y estado de formulario.
- Proveedor sin compras ni productos y campos vacíos: renderizar ceros, tablas vacías y “Sin registrar” sin romper escritorio o móvil; Tasks 3, 4 y 6 cubren el read model y la revisión visual.
